# Audit: PR #1 mlx-taef v0.2.0

Source: `https://github.com/IonDen/mlx-taef/pull/1` (`origin/feature/v0.2.0` at `2b962961bb3a7ab50398d5da82315c2abe852899`)
Date: 2026-05-27
Scope: Product, code, benchmark, documentation, release, and security review of PR #1 against `origin/main` at the fetched PR head.

## Findings

### 1. The regression checker is wired to a schema that `run_showcase.py` does not emit
Severity: High
Refs: `scripts/diff_showcase_report.py:35`, `scripts/run_showcase.py:129`, `_artifacts/showcase_report.json:17`, `tests/test_diff_showcase_report.py:16`

Evidence: `run_showcase.py` returns scenario keys named `taef`, `vanilla_vae`, `ssim_per_pair`, and `ssim_median`; the committed report has that same shape. `diff_showcase_report.py` instead reads `scenario["conditions"]` and `scenario["perceptual"]`, and its tests build only that synthetic shape.

Impact: `scripts/diff_showcase_report.py` can report "No regressions detected" while ignoring the real committed benchmark fields. This invalidates the PR's release claim that future timing and SSIM drift are machine-enforced.

Fix: Align `diff_showcase_report.py` with the actual schema or change `run_showcase.py` to emit the schema the diff checker expects. Add a regression test using `_artifacts/showcase_report.json` or a fixture generated by `run_showcase.py`, not a separate synthetic schema.

### 2. The committed benchmark provenance does not support the published environment claim
Severity: Medium-High
Refs: `COMPARISON.md:5`, `_artifacts/showcase_report.json:4`, `scripts/run_showcase.py:328`

Evidence: `COMPARISON.md` claims "Apple M1 Max, 32 GB" and `mlx-taef 0.2.0`. The committed JSON records `chip: "arm"`, `ram_gb: 0`, and `mlx_taef_version: "0.1.2.dev26+gf9f4df3ee.d20260526"`. The report therefore does not prove the stated machine or the stated package version.

Impact: Reviewers cannot tie the benchmark numbers to the release candidate being reviewed. This weakens the central product artifact in the PR: the measured showcase.

Fix: Record an explicit machine model, RAM, git commit SHA, and package version in the report. Regenerate `_artifacts/showcase_report.json` after the version/tag strategy is settled, or state honestly that the report is from a pre-tag dev build at a specific commit.

### 3. Public live-preview docs do not use the new auto-BN API
Severity: Medium-High
Refs: `README.md:78`, `README.md:100`, `docs/manual-verification.md:17`, `docs/manual-verification.md:45`, `src/mlx_taef/integrations/mflux.py:168`

Evidence: The README and manual-verification examples construct `LivePreviewCallback(...)` without `flux=model`. The implementation only auto-extracts BN stats when `auto_bn` is true, `variant == "taef2"`, and `flux is not None`. The docs still tell users to pass `bn_mean` and `bn_var` manually for exact previews.

Impact: The headline v0.2.0 feature is "auto-bn extraction", but users following the documented happy path still get `resolved_bn == "none"` and color-shifted TAEF2 previews.

Fix: Update the public examples to construct `LivePreviewCallback(flux=model, ...)` before registering it. Keep manual `bn_mean` / `bn_var` as the fallback path for custom integrations.

### 4. README live-preview speed copy contradicts the new measured results
Severity: Medium
Refs: `README.md:11`, `README.md:74`, `COMPARISON.md:29`, `COMPARISON.md:47`

Evidence: README says users can "see each step refresh in <100 ms". The new measured showcase reports 0.260 s median for TAEF2 and 0.185 s median for TAEF1. The README also says the older v0.1.x performance claim was replaced by the subprocess-per-rep measurement.

Impact: The first product promise a user sees overstates the measured v0.2.0 preview latency. That creates avoidable expectation mismatch, especially for FLUX.2 users where the measured median is about 260 ms.

Fix: Replace the `<100 ms` line with the measured v0.2.0 ranges or a variant-specific statement, and point to `COMPARISON.md` for machine-dependent numbers.

### 5. `run_showcase.py --cap-gb` is advertised but has no effect
Severity: Medium
Refs: `scripts/run_showcase.py:62`, `scripts/run_showcase.py:102`, `scripts/run_showcase.py:240`, `scripts/bench_decode.py:155`

Evidence: The CLI exposes `--cap-gb` as an override for the per-condition wired memory cap. The value is never read after parsing: VS-VAE scenarios call `_run_orchestrator(...)` without an override, and live scenarios always call `install_memory_caps()`.

Impact: Users on smaller or larger machines cannot actually use the documented override when reproducing the showcase. That is especially relevant because this PR explicitly adds memory-cap policy and cross-machine cap handling.

Fix: Thread `args.cap_gb` into the bench worker cap path and the live-generation cap path, record the applied override in the report, and add a test that proves `--cap-gb` changes the cap passed to workers.

### 6. Release notes overstate two implementation details
Severity: Medium
Refs: `CHANGELOG.md:19`, `CHANGELOG.md:23`, `src/mlx_taef/integrations/mflux.py:90`, `src/mlx_taef/_memory_caps.py:26`

Evidence: The changelog says auto-BN extracts `running_{mean,var,eps}`, but `_try_extract_bn()` returns only mean and variance and the callback does not store or pass an extracted epsilon. The changelog also says the test suite installs fixed 20 GB / 22 GB caps, while the final implementation clamps caps to the device working-set ceiling.

Impact: These are release-note claims reviewers and users will use to understand the shipped behavior. The current wording makes the BN behavior and memory-cap behavior look more exact and less hardware-dependent than they are.

Fix: Change the changelog to say mean/variance are extracted and `bn_eps` remains the helper default. Update the memory-cap note to describe hardware-aware clamping rather than fixed limits.
