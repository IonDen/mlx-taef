# Audit: mlx-taef v0.2.0 Design
Source: `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md`
Date: 2026-05-26
Scope: Audited the v0.2.0 spec against current `mlx-taef` code, installed `mflux` 0.17.5 API shape, adjacent `mlx-teacache` integration behavior, and current upstream TAESD variant state.

## Findings

### 1. Auto-BN extraction has no real access path to the registered mflux instance
Severity: High

Refs:
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:37`
- `src/mlx_taef/integrations/mflux.py:107`
- `.venv/lib/python3.14/site-packages/mflux/callbacks/callback_registry.py:19`
- `.venv/lib/python3.14/site-packages/mflux/callbacks/generation_context.py:44`
- `.venv/lib/python3.14/site-packages/mflux/models/flux2/model/flux2_vae/vae.py:20`
- `.venv/lib/python3.14/site-packages/mflux/models/flux2/model/flux2_vae/vae.py:43`

Evidence: The spec says `LivePreviewCallback(auto_bn=True)` should walk the registered flux instance for `.vae.bn.running_{mean,var}`. Current `LivePreviewCallback.__init__` receives only callback-local options and BN arrays; it has no `flux`, `vae`, registry owner, or model argument. In `mflux` 0.17.5, `CallbackRegistry.register()` only appends the callback to subscriber lists, and `GenerationContext.in_loop()` calls `call_in_loop()` with generation data only. The FLUX.2 BN stats do exist on `Flux2VAE.bn`, but the callback is never given the object that owns them.

Impact: An implementation following this spec cannot actually auto-resolve BN from normal `flux.callbacks.register(LivePreviewCallback(...))` usage. It will either silently fall back to identity BN for `taef2`, or require brittle global introspection not described by the spec.

Fix: Make ownership explicit. Add either `LivePreviewCallback(..., flux: object | None = None)` or a `LivePreviewCallback.from_flux(flux, ...)` constructor that extracts `flux.vae.bn.running_mean`, `running_var`, and `eps` immediately. Keep explicit `bn_mean` / `bn_var` precedence, and define `resolved_bn` as `explicit`, `auto`, or `none`. If the API must stay constructor-only, remove auto-BN from v0.2.0 and keep the manual BN contract.

### 2. The showcase memory cap would apply the tiny TAEF budget to the full-VAE baseline
Severity: High

Refs:
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:39`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:132`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:139`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:149`
- `README.md:72`

Evidence: The spec assigns `taef2` a `memory_cap_hint_gb` of 2 GB and says decoder workers apply the cap before model load. The same benchmark scenario also includes a `vanilla_vae` condition. The current README's measured comparison says the full FLUX VAE peaks around 9.6 GB, so a worker capped at the `taef2` hint is not a valid environment for the full-VAE baseline.

Impact: `taef2_vs_vae` can fail before measuring the baseline, or the implementation may widen the cap for all conditions and stop enforcing the TAEF memory claim. Either outcome undermines the showcase result because speed and memory numbers are no longer measured under clearly separated constraints.

Fix: Split memory policy by measured condition. Use the variant hint only for the TAEF decode condition, and use a separate explicit `full_vae_cap_gb` or uncapped baseline worker for full VAE. Record each worker's cap in `_artifacts/showcase_report.json` so the comparison is auditable.

### 3. The `showcase` extra does not install the runtime needed by the advertised showcase
Severity: Medium-High

Refs:
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:97`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:236`
- `pyproject.toml:33`
- `pyproject.toml:47`

Evidence: The spec adds `showcase = ["mlx-teacache>=0.6,<0.7"]`, while the same spec says live-preview, combined, and `*_vs_vae` scenarios depend on `mflux`. Current `pyproject.toml` keeps `mflux` and `image` as separate extras, and the test group includes `mflux>=0.17`; `showcase` as written would not install the primary showcase dependency. The spec also requires SSIM output but does not name a dependency or in-tree implementation for SSIM.

Impact: A user or release runner installing the documented showcase extra can get a mostly skipped or incomplete showcase instead of the committed comparison report. This weakens the release claim because the reproducibility path does not install what the command needs.

Fix: Make `showcase` a complete runtime extra, for example `mflux>=0.17,<0.18`, `mlx-teacache>=0.6,<0.7`, `pillow>=10`, and either `scikit-image` or a documented in-tree SSIM implementation. If the showcase depends on exact `mflux` callback semantics, keep the upper bound until compatibility is rechecked.

### 4. The upstream-variant check is pointed at releases, but upstream variants are already present outside releases
Severity: Medium-High

Refs:
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:22`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:87`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:323`
- `src/mlx_taef/variants.py:57`
- `https://github.com/madebyollin/taesd`

Evidence: The spec says to poll `gh api repos/madebyollin/taesd/releases` and frames TAESD3 as a future item "if upstream ships." The upstream TAESD README currently lists TAESD3 and TAESANA alongside TAEF1 and TAEF2 in its variant table. The local library currently defines only `taesd`, `taesdxl`, `taef1`, and `taef2`.

Impact: The v0.2.0 roadmap can ship stale wording that treats already-known upstream variants as hypothetical. A releases-only check can also miss upstream model files or README updates, so it is not a reliable source for variant support status.

Fix: Change the check to inspect upstream repo contents, README variant table, or the relevant Hugging Face model IDs, not only GitHub releases. In the roadmap, name TAESD3 and TAESANA as known unsupported variants deferred from v0.2.0 unless this release intentionally adds them.

### 5. Committed-artifact policy contradicts itself
Severity: Medium

Refs:
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:102`
- `docs/superpowers/specs/2026-05-26-mlx-taef-v0.2.0-design.md:222`
- `.gitignore:1`

Evidence: The spec lists `tests/fixtures/showcase_latents/*.safetensors` as committed assets, then later says `tests/fixtures/showcase_latents/` is gitignored by default and committing binaries is optional. The current `.gitignore` does not ignore `tests/fixtures/showcase_latents/` or `_artifacts/`.

Impact: Implementers do not have a clear release policy for the latent fixtures that underpin the report. If latents are not committed, the committed report is not reproducible from exactly the same input unless the capture contract is very strong. If they are committed, the spec's optional/gitignored wording and current ignore file are wrong.

Fix: Pick one policy. For reproducible release artifacts, commit the latent `.safetensors` files and `.sha256` sidecars, and make sure `.gitignore` allows them. For a lightweight repository, remove the latents from "Committed assets," add the intended ignore rules, and require the report to include prompt, seed, model identifiers, capture command, and latent SHA disclosure.
